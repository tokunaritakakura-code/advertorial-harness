# 3. 実行手順（毎回この順）

1. **参考を1本選ぶ**: 商品と悩みが一番近く、型.md の分岐（定期か買い切り・言いにくいか・医薬品か）が同じ側の参考を `refs/` から1本。理由を1行。広告の文字起こしの最後の3行を書き出す
2. **段に割る・移植表**: 写す所（変えない）＝段の並び・段の数・画像の置き方・数字の出し方。任せる所＝うちの商品に合わせた言い回し（直訳で同じ効果が起きるなら直訳）。参考の段を上から全部、左に参考・右にうちの日本語。段ごとに「仕事」「心理」「ビジュアル」（画像の中身・人と物・画像の中の文字・大きさと置き場。参考の画面を見て書く）と「コピー」（見出し・本文・強調・注記）を分け、うちの物も両方を1段ずつ埋める。参考の段ごとに「型の段」（型.md の固定の何段目か。迷ったら、その段の仕事が同じ型の段）と「参考の画像」（HTML の中で何番目の画像か）の列も書く。頭に広告からの受け渡しの表。うちの事実は本番の店から取り、出どころ（店のURL・Vault の商品ファイルと行）を右に
3. **必ず入れる物を足す**: `~/Documents/Obsidian Vault/ec/構造/型/_必ず入れる物.md`（決めたことの「仕掛けの棚」はこの1枚）の一覧を、足し方の決まり（場所・見た目・文・印）どおりに移植表へ足す。場所は参考の中で同じ仕事をしている段（最悪の結末はアンケート型なら頭の絵の下、値段は値段の札と申込の段）。見た目は参考の中の同じ形の部品を使い、文は前後に1文でつながるように書く。最悪の結末は、頭の絵が縦長の時は段の幅を390pxにし、枠の文を1行25字以内にして1280×800の最初の画面にも収める。値段は「1日あたりの文 → 今のパッド代と比べる文 → 値段の札の画像 → 縦長の値段画像」の順に並べる。型.md の分岐で足す段（例: バレない配送）は、選んだ参考にその段がある時だけ足す（参考との差を0にするため）
4. **組む**: 移植表どおりに `index.html` を1本書く。段ごとに `data-dan="<型.md の段の番号>"`、ボタンに `data-cta`。問いは1問ずつ枠に入れて枠に `data-q="1"`〜 を付け、`Q1.` の形で見出しにし、答えのボタンに `data-answer`（検査が問いの数とボタンをこの印で数える）。どの答えでも次の問いへ進み、3問目の後にお礼の段を出す（JS は index.html の中に）。答えた問いのボタンからは `data-answer` を外し、選んだ答えを示す帯に替える（残すと幅の検査が同じ問いを押し続ける）。見た目は参考に合わせる（短い行・赤字・黄色の下線・絵文字・画像はスマホの幅いっぱい）。`<meta name="robots" content="noindex">` を入れる。テスト用に決めた数字・人・声は `テスト用に決めた値.md` に書く。テストの時は、商品情報で分からない所を止めずに予測して作り、作り終えたら予測した事（何を・どう予測したか・根拠のファイル）を `予測した事.md` に一覧で書く（2026-10-10 本人）
5. **画像**: 先に `python3 ~/.claude/skills/quiz-jp-copy/scripts/参考の画像を落とす.py <参考の HTML か URL> <作業フォルダ>/参考の画像/` で参考の画像を出てくる順に落とす（mp4 は1コマ目、webp・avif・gif は png にする）。参考の同じ段の画像を `mcp__chatgpt-image__generate_image` に添付し、人物を日本人・商品を自社（本番の店の商品画像を添付）に替える。構図・画像の中の字の置き方は参考のまま。画像の中の文字は、同じ文を `alt` にも書く（機械の検査が読むため）。細長い画像（縦÷横 0.4未満・2.5超）は作らない。体の3D図が入った参考の画像で生成が `IMAGE_GEN_UNAVAILABLE` で落ちたら、図の部分を切って文字の置き方の部分だけ添付し直す。値段の札の画像は参考の形のまま、通常の値段に打ち消し線を入れて作る。縦長の値段画像は作った後に縦を切って 幅÷高さ 0.70 にする（生成の縦長は 0.667 で下限 0.67 を割る）
6. **型の検査**: `型の検査.py <index.html> --店 <店のURL>` が終了コード0になるまで、×の段を3か4に戻って直す
7. **幅と押せるか**: `幅の検査.py <index.html> --押す 3`（行の最後に1〜2文字だけ落ちた所も数える）と `記事の仕上がり検査.py` が終了コード0。`記事の仕上がり検査.py` の「強調の頻度」はここちドライの記事の基準で、この型（ほぼ全部の行に赤字か黄色の下線）とは合わないので、その1項目だけは最終確認 D3 で見て、理由を `最終確認.md` に書く
8. **別の AI の審査**: 新しい文脈の Opus のサブエージェント（`model: "opus"`・`run_in_background: false`）に、参考の段の表・参考の画面・出来た物の画面（幅390）・移植表・この最終確認を渡し、段ごとの効果・分かりやすさ・型の固定16段を見させる。T3 は別の審査役に分けて、参考も足した場所も見せず、出来た物の画面（幅390を上から全部）だけを渡して「浮いて見える・流れが切れる所」を強・中・弱つきで挙げさせる。答え合わせは作る側が `data-tasu` の段の位置で行い、強か中で挙がった足した段があれば手順3に戻して直す（足した場所を教えると必ず当たり、参考と並べると参考に無い物が全部挙がるので、どちらも確かめにならない。2026-10-10 1回目の通しで2回起きた）。2回目からの審査は、前の回の直すべき所が直ったかを先に○×で見させ、そのうえで新しく FAIL に当たる物だけを挙げさせる（毎回一から見ると、回ごとに別の所を挙げて収まらない）。審査役は通知で返ってくることがあるので、返るまで手順9の下書きを進め、判定を見てから箱を付ける。審査のファイルは、1行目に `PASS` か `FAIL: <理由>`、次に「## 受け取った物」の節（参考の段の表・参考の画面・出来た物の画面・移植表・最終確認の5つを必ず渡し、全部並べさせる）、その後に基準ごとに1行ずつ「前の回の直し／段ごとの効果／型の固定／分かりやすさ: <理由> → ○か×」（理由を先に書いてから○×）。入力が欠けても審査役は PASS を出し、まとめた1行の判定は何を直すか教えないため。保存先は `審査_<何本目>_<回>.md`。読み手の目は `読み手の目_<何本目>_<回>.md` に、1行目に作る側が答え合わせの結果（足した段が強・中で挙がっていなければ `PASS`）を書き、2行目から審査役の一覧をそのまま。作った自分では判定しない
9. **最終確認**: 上の箱 A〜F と T を全部埋め、`最終確認.md` に書く。kata-tsukuru から呼ばれた時は、同じ番号で `e2e/結果_<何本目>.json` の「最終確認」にも書く。×はその箱の手順へ戻る。審査の後に出来た物を1文字でも直したら、手順8の審査をもう一度通す
